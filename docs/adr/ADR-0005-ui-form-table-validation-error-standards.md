# ADR 0005: มาตรฐาน Form, Data Table, Thai DatePicker, Client Validation และการจัดการ Error ให้เป็นมิตรกับผู้ใช้งาน

## Status
Accepted (วันที่ 2026-11-01)

## Context
ระบบบริหารจัดการเทศบาลดิจิทัล OTP 2025 มีผู้ใช้งานหลักคือเจ้าหน้าที่เทศบาลและประชาชนทั่วไปที่มีอายุ 40 ปีขึ้นไป ซึ่งส่วนใหญ่ไม่มีความเชี่ยวชาญด้านคอมพิวเตอร์ ในเวอร์ชันเดิมระบบประสบปัญหาสำคัญด้าน UX หลายประการ:
1. การตรวจสอบฟอร์มพึ่งพา HTML5 Native Validation ของเบราว์เซอร์ ซึ่งแสดง Tooltip ตัวหนังสือเล็ก เป็นภาษาอังกฤษ และพฤติกรรมไม่เหมือนกันในแต่ละเบราว์เซอร์
2. ตารางข้อมูลโหลดข้อมูลทั้งหมดมาเรนเดอร์บนเบราว์เซอร์ (Client-side dump) ส่งผลให้เบราว์เซอร์ค้างเมื่อข้อมูลมีจำนวนมาก
3. วันที่ไม่มีความเป็นเอกภาพ บางที่แสดง พ.ศ. บางที่แสดง ค.ศ. ทำให้ผู้ใช้สับสนและบันทึกข้อมูลผิดพลาด
4. เมื่อเกิดข้อผิดพลาดจาก Backend หรือ Database ระบบแสดง Technical Exception Jargon เช่น `SQLSTATE[23000]`, `cURL error 28`, `Unprocessable Entity` ซึ่งสร้างความตกใจและสับสนแก่ผู้ใช้
5. เมื่อกรอกข้อมูลผิดหลายช่อง ระบบแสดง Error พร้อมกัน 5–10 รายการ ทำให้ผู้ใช้เกิด Cognitive Overload และท้อถอยในการใช้งาน
6. การแจ้งเตือนขาดความสอดคล้อง ปะปนกันระหว่าง `alert()` ของเบราว์เซอร์, Toast และ Popup Modal

## Decision
กำหนดมาตรฐานสถาปัตยกรรม UI/UX สำหรับ Form, Table, DatePicker, Validation และ Error Feedback ทั่วทั้งระบบดังนี้:
1. **Form Standards:** กำหนดให้ใช้โครงสร้าง Clean White Card ขอบมน 12px ช่องกรอก (Input, Select) และปุ่ม (Button) มีความสูงขั้นต่ำ 48px–52px ฟิลด์บังคับกำกับด้วยเครื่องหมาย `*` สีแดง และปุ่ม Action Bar ด้านล่างมีปุ่ม "บันทึกข้อมูล" อยู่ฝั่งขวา และ "ยกเลิก" อยู่ฝั่งซ้ายเสมอ
2. **Search & Filter Standards:** แยกส่วนค้นหาเป็น Filter Card ด้านบนของตารางอย่างชัดเจน มีทั้งค้นหาด่วนและตัวกรองละเอียด พร้อมปุ่ม "ค้นหา" และ "ล้างค่าการค้นหา" เพื่อรีเซ็ตค่าได้ในคลิกเดียว
3. **Data Table Standards:** ตารางแสดงผลข้อมูลขนาดใหญ่ทั้งหมดต้องใช้ DataTables แบบ Server-Side Ajax (`serverSide: true`, `ajax: "..."`) พร้อมระบบแบ่งหน้า (Pagination) ตัวเลขใหญ่ และแสดงสถานะกำลังโหลด (Loading Overlay) เสมอ
4. **Thai Buddhist Era DatePicker:** ช่องเลือกวันที่ต้องแสดงผลและให้ผู้ใช้เลือกเป็น **ปี พ.ศ. เสมอ** ในรูปแบบ `วัน/เดือน/ปี` (เช่น `01/09/2568`) แต่ในระดับ Database และ Backend ต้องจัดเก็บเป็น **ปี ค.ศ. เสมอ** ในรูปแบบ ISO-8601 `YYYY-MM-DD` (เช่น `2025-09-01`) โดยใช้กลไก JavaScript Dual-Binding แปลงค่าอัตโนมัติ
5. **Form Validation:** ห้ามใช้ HTML5 Default Validation โดยใส่ attribute `novalidate` บน `<form>` ทุกตัว และใช้ Client Validation Library ควบคู่กับคลาส `.is-invalid` และ `.invalid-feedback` ของ Bootstrap 5 พร้อมข้อความช่วยเหลือภาษาไทยที่สุภาพ
6. **Single-Error Filtering & Non-Technical Errors:** หากเกิด Error หลายรายการ ระบบต้องกรอง (Filter) นำเฉพาะ **ข้อผิดพลาดแรกสุด (First Error Only)** มาแสดงผล พร้อมเลื่อนหน้าจอ (Auto-scroll) และโฟกัสไปยังฟิลด์นั้นทันที ข้อความ Error ต้องแปลงเป็นภาษาไทยที่เข้าใจง่ายตามรหัสใน `docs/ERROR_CODE_MAPPING.md` ห้ามมี Technical Jargon หลุดถึงผู้ใช้
7. **Two-Tier Feedback Consistency:** กำหนดรูปแบบการแจ้งเตือน 2 ระดับอย่างสอดคล้องกัน:
   - **SweetAlert2 Modal:** สำหรับเหตุการณ์สำคัญที่ต้องรับรู้หรือยืนยันผล (Confirmation / Critical Actions / บันทึกสำเร็จ / ลบข้อมูล)
   - **SweetAlert2 Toast:** สำหรับเหตุการณ์เบื้องหลังที่ไม่ขัดจังหวะการทำงาน (Auto-save / คัดลอกสำเร็จ / เปลี่ยนสถานะย่อย)

## Consequences
- **Positive:** ผู้ใช้งานอายุ 40+ ปีและผู้ใช้ทั่วไปได้รับประสบการณ์ที่ใช้งานง่าย สบายตา ไม่สับสนเรื่องปี พ.ศ./ค.ศ. ลดข้อผิดพลาดในการกรอกข้อมูล ลดภาระงานของทีม IT Support/Helpdesk และตารางทำงานเร็วขึ้นด้วยการโหลดข้อมูลแบบ Server-Side Ajax
- **Negative:** เพิ่มความซับซ้อนในการพัฒนา โดยนักพัฒนาต้องเขียนโค้ดและทดสอบทั้งฝั่ง Client Validation, Date Transform และลงทะเบียน Mapping Error Code ทุกครั้งที่สร้างโมดูลใหม่
- **Constraints (สำหรับ AI Agent):**
  - ทุก `<form>` ที่เป็นฟอร์มรับข้อมูลหรือค้นหา **ต้องมี attribute `novalidate` เสมอ** ห้ามปล่อยให้ HTML5 Browser Tooltip ทำงานเด็ดขาด
  - **ห้ามส่ง Technical Error หรือ Database Exception ตรงไปยัง UI เด็ดขาด** ต้องแปลงเป็นรหัสและข้อความภาษาไทยที่เป็นมิตรตาม [`docs/ERROR_CODE_MAPPING.md`](file:///Users/poppy.geidtiphong/Documents/workspace/homework/otp2025/docs/ERROR_CODE_MAPPING.md) เสมอ
  - หากการตรวจสอบข้อมูลพบข้อผิดพลาดหลายรายการ **ต้องกรองและแสดงผลเฉพาะ Error แรกสุด (First Error) เท่านั้น** พร้อม Scroll & Focus ไปยังฟิลด์นั้น
  - ข้อมูลวันที่ในหน้าจอ UI **ต้องแสดงผลและเลือกเป็นปี พ.ศ. เสมอ** (วัน/เดือน/ปี พ.ศ.) แต่เมื่อส่ง Request หรือบันทึกลง Database **ต้องแปลงเป็นปี ค.ศ. รูปแบบ `YYYY-MM-DD` เท่านั้น**
  - ตารางข้อมูล DataTables **ห้ามดึงข้อมูลทั้งหมดมาแสดงฝั่ง Client เด็ดขาด** ต้องกำหนด `serverSide: true` และมี Pagination เสมอ
  - ปุ่มกดและช่องกรอกข้อมูลทั้งหมด **ต้องมี Touch Target ความสูงขั้นต่ำ 44px–48px** เพื่อรองรับผู้สูงอายุและอุปกรณ์สัมผัส/มือถือ
